# TUJUAN

Refactor halaman `Tagihan` customer agar tidak lagi terlihat seperti halaman `Pesananku`.

Konsep baru:

**Tagihan = financial center customer**

Halaman ini harus berfungsi seperti halaman tagihan pada aplikasi finansial seperti SPayLater/SPinjam:

- menunjukkan berapa kewajiban pembayaran yang masih harus dibayar
- menunjukkan total nominal outstanding
- menyediakan action untuk melakukan pembayaran
- menyimpan riwayat pembayaran yang sudah dilakukan

Halaman Tagihan TIDAK boleh menjadi duplicate order history.

Jangan tampilkan card produk, thumbnail produk, variant, daftar item, atau detail shipment di halaman ini.

Informasi produk dan lifecycle order tetap menjadi tanggung jawab halaman `Pesananku`.

---

# STRUKTUR HALAMAN

Buat halaman Tagihan customer dengan struktur utama:

## 1. Header

Contoh:

`Tagihan`

Deskripsi singkat:

`Kelola pembayaran yang masih harus diselesaikan dan lihat riwayat pembayaranmu.`

Jangan gunakan istilah backend yang terlalu teknis.

# 2. FINANCIAL SUMMARY

Di bagian atas halaman, tampilkan summary yang ringkas.

Contoh:

`Total yang harus dibayar`

**Rp425.000**

`2 tagihan aktif`

Summary harus dihitung dari seluruh kewajiban pembayaran customer yang masih outstanding.

Jangan hanya menghitung jumlah order.

Satu order dapat memiliki lebih dari satu kewajiban pembayaran.

Contoh:

Order A:
- Pelunasan Rp250.000
- EMS & Pajak Rp75.000

Maka:

- active billing count = 2
- total outstanding = Rp325.000

Gunakan logic existing sebagai source of truth.

# 5. ACTIVE OBLIGATION LOGIC

`1 order = 1 tagihan`

# RIWAYAT PAYMENT DATA

Gunakan payment transaction existing.

Prioritaskan transaksi yang:

- sudah diverifikasi
- memiliki nominal pembayaran
- memiliki tanggal pembayaran/verifikasi

Urutkan:

`terbaru -> terlama`

Jika memungkinkan, group berdasarkan bulan dan tahun.

Contoh:

Oktober 2026

September 2026

Agustus 2026

Jika grouping membuat implementation terlalu kompleks untuk current view architecture, chronological list tetap boleh, tetapi desain harus tetap terasa seperti transaction ledger.

---

# PAYMENT HISTORY CONTENT

Setiap row dapat menampilkan:

- jenis pembayaran
- batch
- order code
- tanggal pembayaran/verifikasi
- nominal
- status

Contoh status:

`Terverifikasi`

Jangan menampilkan seluruh detail order.

Jika customer perlu melihat context order lebih jauh, order code atau row dapat mengarah ke detail order existing.

# PAYMENT HISTORY ≠ PAID ORDER HISTORY

Ini sangat penting.

Jangan membuat logic:

"order yang sudah lunas = satu row riwayat pembayaran"

Yang harus ditampilkan adalah actual payment transaction.

Contoh:

Satu order memiliki:

DP:
Rp100.000

Pelunasan:
Rp200.000

Maka Riwayat Pembayaran boleh memiliki dua transaction entries:

DP Pesanan        Rp100.000  
Pelunasan         Rp200.000

Bukan:

Order ABC         Rp300.000

kecuali existing database memang hanya menyimpan satu aggregate payment dan tidak memiliki ledger transaction yang lebih detail.

Gunakan data existing yang tersedia.

# ACCEPTANCE CRITERIA

Task dianggap selesai jika halaman Tagihan memiliki behavior berikut:

## Tagihan Aktif

Menampilkan hanya hal yang perlu dibayar.

Tidak menampilkan produk.

Dapat menampilkan:

- DP
- Pelunasan
- EMS & Pajak

Menampilkan:

- nominal
- batch
- order code
- due date jika tersedia
- payment status
- payment method
- CTA bayar

## Riwayat Pembayaran

Menampilkan transaction history customer.

Tidak menjadi clone Pesananku.

Menampilkan:

- jenis transaksi
- nominal
- tanggal
- batch/order reference
- verification status

## Financial Summary

Menampilkan:

- total outstanding
- jumlah active obligations

## Profile

Badge Tagihan konsisten dengan active obligations.

## UX

Customer harus dapat memahami halaman hanya dengan tiga pertanyaan:

1. Berapa yang harus saya bayar?
2. Untuk apa pembayaran tersebut?
3. Apa saja yang sudah pernah saya bayar?

Jika halaman masih membutuhkan customer membuka card produk atau memahami struktur internal order hanya untuk mengetahui tagihannya, refactor belum selesai.
